# C4 262k capacity activation

**Recorded outcome:** the coordinated four-rank transition, the post-boot functional gates
and the full-context capacity proof all passed, and no promotion followed. This is a
lifecycle and capacity record only: no promotion, no new baseline and no performance claim.
No native Rigmark suite ran in this window, so the record supports no throughput, latency,
prefill or concurrency value at all.

Coverage was one authorized coordinated transition from the accepted E03 recipe to the C4
candidate, eight full-context capacity requests, and one single-request functional smoke
afterwards. The eight capacity requests are four distinct request bodies submitted twice:
a cold phase of four and a replay phase of the same four digests. Native Rigmark suites
completed: zero. Native Rigmark requests: zero. There is no native performance receipt.

The measured recipe held the request limit at 262,144 tokens and changed three things
relative to the accepted E03 reference: the SparkCache connector was swapped to the C4 file
with sha256 `a37309f1…9262`, the KV pool was cut from 16,106,127,360 to 12,884,901,888 bytes
per rank, and `MAX_NUM_SEQS` was cut from six to four. All four ranks were verified to be
serving exactly that recipe: `--max-num-seqs 4`, `--max-model-len 262144`,
`--kv-cache-memory-bytes 12884901888`, `--max-num-batched-tokens 8192` and
`--block-size 2304`, 4/4 PASS. The engine reported 640 KV blocks per rank. The C4 connector
is not tracked in this repository; `scripts/node/sparkcache/SHA256SUMS` pins the E03 replay
connector `5893f874…2266` and contains no entry for the C4 digest, and the candidate overlay
named in the private execution summary is not present in the current checkout. The recipe is
therefore reproducible only from the recorded launcher flags and the connector digest.

Lifecycle and functional verification all returned exit code 0. The base stack came down in
9.562 seconds, the candidate deploy took 34.56 seconds and the coordinated candidate start
took 1,012.21 seconds. The C4 connector payload installed with mode 0600 and the expected
digest on all four ranks. Static verification reported 160 PASS / 0 FAIL, the fabric check
reported 8/8 jumbo directions, and live verification reported 166 PASS / 0 FAIL. `/health`
first returned 200 at 19:59:26.749Z and both post-boot functional gates passed 3.078484
seconds later, far inside the two-minute deadline. The one-request smoke after the capacity
phase returned HTTP 200 with a correct 8-token answer and finish reason `stop`, and the three
idle samples that follow it show 0 requests running. The final offline `./scripts/check.sh`
exited 0. The candidate was left healthy and serving; the base `cluster.env` stayed at the
unchanged E03 recipe and the candidate overlay was not persisted, so the next autostart
recipe remained base E03.

All eight capacity requests returned HTTP 200 with 261,632 prompt tokens, 512 completion
tokens and finish reason `length`, and the replay phase reused the four cold request digests
unchanged. Each of the four ranks committed four cache entries of 260,352 tokens in the cold
phase and then verified four loads of 260,352 tokens in the replay phase, with zero store
failures, zero restore rejections, zero evictions and zero preemptions across both phases.
The engine counted 1,041,408 externally restored prefix tokens and no local prefix hits.

These elapsed figures are wall-clock phase durations for a capacity probe, not benchmark
measurements, and they are not comparable with any frozen record.

The limitations are material. The 625-block figure used to size the C4 candidate is a
modeled capacity budget, not observed occupancy: the metrics review records zero samples with
four requests running and at least 625 total blocks, and its first qualifying sample is null.
The highest common occupancy actually observed during the four-running replay interval was
581 blocks including the null block. The cold phase never showed four simultaneous
near-limit contexts; its peak was two running with two waiting. Per-rank active residency is
not independently measured and there is no one-to-one attribution from a verified restore to
a specific request, so the four-context replay overlap rests on sixteen samples at four
running together with four verified restores on every rank. Connector counters such as
store-skipped-busy and the per-group block decomposition are not exposed live. Host memory
minima are sampled observations at roughly half-second intervals, not bounds: rank 0 fell to
4.934 GiB MemAvailable during the cold phase and 4.663 GiB during replay, while the other
three ranks stayed above 8.87 GiB, and the copy peak of about 3.3 GiB remains modeled. The
OOM review found zero earlyoom and zero kernel interventions on all four ranks, but the
earlyoom journal window was empty on ranks 2 and 3, so the zero-intervention result there
rests on the kernel journal alone. The `scripts/check-f0.py` identity check did not complete
from the orchestrating workstation, which could not reach the service endpoint, so the served
recipe was confirmed from the per-rank launcher flags and the on-cluster live verification
instead of from that check.

Above all, no native Rigmark suite was executed, so this window cannot reproduce, support or
challenge the frozen 2026-09-19 E03 performance reference, whose bytes are unchanged. The C4
recipe was superseded first by the 2026-09-21 native admission windows recorded as
2026-09-21-c4-native-admission-28 and 2026-09-21-c4-no-admission-3x, and then by the C5
return to the E03 replay connector and 15 GiB KV per rank.
