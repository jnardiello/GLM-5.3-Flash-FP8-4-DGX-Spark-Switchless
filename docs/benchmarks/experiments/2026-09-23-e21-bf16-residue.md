# E21: 8-bit weights for the residual BF16 attention projections

**Recorded outcome: promote, accepted by the owner.** Three complete native Rigmark
suites, 162 requests, on one retained candidate load. C4 +9.88% and C2 +4.68% with every
suite outside the E03 range, prose +4.02%, no primary metric worse beyond measured noise.
The result became the [September 23 E21 reference](../baselines/2026-09-23-e21.md).

## Why this candidate

The decode kernel profile left a large BF16 GEMM residue after E20, which converted only
the 34 KDA input projections, 9.06% of decode kernel time, for roughly a 4–5% end-to-end
gain. Converting the KDA output projection alone would have been 3.00% of kernel time,
about 1.5% end-to-end and inside the measured noise floor of about 1.7–1.8% on the
primary concurrency metrics. So the candidate took the whole remaining attention residue
that the same mechanism can serve.

The MLA projections turned out to be block FP8 in the checkpoint: the vendor model code
passes a quantization config to MLA layers only for `modelopt_mixed` checkpoints, so for
this `fp8` checkpoint it dequantizes them to BF16 on load and serves them as BF16 GEMMs.
E21 converts them to INT8 with the E20 mechanism rather than switching to a native FP8
path, which would have been a second, unmeasured mechanism.

A tuned fused-MoE configuration for the M=16 and M=24 buckets was considered first and
rejected without a window: a recovered 2026-09-04 measurement had already shown that
tuning those buckets lowered C4 throughput by 6.7% against the upstream defaults.

## What changed

| Family | Layers | Shape per rank (N × K) | Stored in the checkpoint as |
| --- | ---: | --- | --- |
| KDA `o_proj` | 34 | 4096 × 2048 | BF16 |
| MLA `o_proj` | 11 | 4096 × 4096 | block FP8, dequantized on load |
| MLA `fused_qkv_a_proj` | 11 | 2048 × 4096 | block FP8, dequantized on load |
| MLA `q_b_proj` | 11 | 4096 × 1536 | block FP8, dequantized on load |

Excluded: the KDA f/g gates, which drive a recurrent state; MLA `kv_b_proj`, which the
attention backend absorbs; the sparse-attention indexer; `lm_head`; and the DFlash2
drafter. Sources, manifest, overlay and tests are in
[`scripts/node/experiments/e03/bf16-residue/`](../../../scripts/node/experiments/e03/bf16-residue/README.md).

## Pre-window checks

- A CPU emulation on real checkpoint weights measured relative weight error of
  0.65–0.71% and output error of 0.54–0.91% across the four families, the same order as
  E20's 0.70%. The double quantization of the MLA weights did not raise the error.
- The installed `DeepSeekV2FusedQkvAProjLinear`, read from the serving image, has a
  low-latency path that reads the weight directly, but it activates only for a 2112 × 7168
  BF16 weight on compute capability 9.0 or family 10. It cannot activate here.

## Measurement

One coordinated transition from the previous operational overlay to the candidate took
724 seconds to `/health` 200. Both functional gates passed 3.1 seconds later, and the
four-rank identity matched: module hashes, flag and the E21 boot signature with 67
modules on every rank. The three suites followed the frozen E03 source, prompts and
settings, through the same kind of local tunnel as the reference, with a fresh cache salt
per suite and the same host memory sampler. No container restarted during the series.

| Metric | E03 | E21 | Change |
| --- | ---: | ---: | ---: |
| Code C4, aggregate | 86.932 tok/s | 95.524 tok/s | +9.88% |
| Code C2, aggregate | 61.834 tok/s | 64.726 tok/s | +4.68% |
| Code C1, end-to-end | 40.233 tok/s | 40.718 tok/s | +1.21% |
| Code decode | 53.809 tok/s | 54.945 tok/s | +2.11% |
| Prose decode | 31.186 tok/s | 32.441 tok/s | +4.02% |

All 16 metrics, per-run values and dispersion are in the
[baseline report](../baselines/2026-09-23-e21.md#performance).

## Evidence and limits

- 162/162 requests completed visibly with zero native, protocol or runtime errors. The
  code completion gate is 13/15 because two long code requests reached the 8,192-token
  budget; E03 recorded 15/15.
- C1 run 1 was 38.760 tok/s, below the E03 range; runs 2 and 3 recovered to 40.718 and
  40.944 tok/s, matching the known unisolated C1 variability.
- C1 and C2 per-stream TTFT rose by 2.04% and 2.45%; C4 per-stream TTFT fell by 5.07%.
- Minimum sampled available memory rose on every rank, on rank 0 from 2.26–2.36 GiB to
  3.22–3.58 GiB. Zero GPU OOMs, allocation retries and host OOM kills.
- The estimate before the window was 3.0–3.6% end-to-end, from single-stream decode
  kernel shares. The measured concurrency gains are larger; the kernel-time model does
  not predict throughput under concurrency.
- By owner decision, promotion used launcher-command parity with the measured candidate
  instead of a separate reproduction run.
