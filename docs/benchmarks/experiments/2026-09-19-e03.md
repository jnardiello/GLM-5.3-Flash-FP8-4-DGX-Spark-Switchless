# E03: FP8 mHC prefill sharding

**Outcome: decision_required.** Three complete native Rigmark runs (162 requests)
confirm faster cold prefill and C2. Small code, C4 and prose median declines are
compatible with observed variability and are not treated as rejection criteria,
consistent with the owner's assessment. Slower 32K/64K replay remains a tradeoff.
The healthy opt-in candidate is retained online pending the promotion decision.

The reference is the unchanged [September 19 baseline](../baselines/2026-09-19.md):
exactly two accepted native runs and 108 requests. It was not remeasured. E03 completed
**3/3 runs, 162/162 requests**, with no exclusions, runtime, transport, protocol or
receipt-validation errors. All runs used one corrected-candidate weight load.

Cold-prefill and C2 throughput exceed both frozen reference run values in every E03

They remain visible in the table rather than becoming a reason to reject E03.
Replay 32K is slower in two runs and replay 64K in all three: this is the principal
measured cost to weigh against faster cold prefill and C2 before promotion.

## Replay follow-up

The owner retained E03 online and requested a focused replay improvement. The
following analysis reuses the saved receipts; it added no inference requests,
GPU contexts or lifecycle actions. Absolute first-visible latency makes the
measured cost clearer than effective prefill throughput alone:

| Replay | Frozen baseline TTFT | E03 TTFT | Difference |
| --- | ---: | ---: | ---: |
| 32K | 0.930 s | 0.991 s | +61 ms |
| 64K | 1.849 s | 1.895 s | +46 ms |

These are medians of the native per-run latency medians, using the same two and
three accepted runs. First-visible latency equals TTFT for every prefill sample.
All four ranks restored the same token counts and byte sizes as the reference:
32,256 tokens / 237.4 MiB at 32K and 64,512 tokens / 427.2 MiB at 64K. The remaining
512/1,024 target tokens are below E03's 6,912-row sharding guard. Publication waits
remain about 6 ms. Median slowest-rank restore durations are approximately
510 → 511 ms at 32K and 1,089 → 1,096 ms at 64K. These logs do not explain the full
TTFT difference or establish an mHC defect.

A separate [prepared replay candidate](../../../scripts/node/experiments/e03/replay-views/README.md)
removes one complete snapshot copy in the Python restore path. It reuses validated
page spans as memory views, retaining per-layer writable copies, block placement,
integrity checks and stream synchronization. Model computation and cache format
remain identical, so it keeps E03's existing cache namespace. It changes only the
connector mount and hash; four launcher previews verified that invariant.

The actual old/new restore methods passed a compact CPU check in the pinned R10
environment with CUDA disabled: heterogeneous pages and physical slots match
exactly, untouched blocks stay intact and damaged framing is rejected. A separate
local CPU allocation proof with the observed body sizes removes about **237 MiB /
427 MiB per rank** from this materialization step. This is a temporary-copy reduction,
not a measurement of total process memory or serving latency. The candidate has
no GPU or Rigmark result in that preparation record.
[Preparatory evidence and source hashes](../../historical_benchmarks/experiments/2026-09-19-e03/replay-follow-up.json)
retain the per-run timings, proof scope and limitations. Its four-rank GPU checks
and native measurement are recorded in the separate
[replay candidate report](2026-09-19-e03-replay-views.md). E03's accepted results and
the frozen reference are unchanged.

## Integrity and memory

All **162/162 streams** completed with visible output and available first-visible
latency. Exact prefill input counts matched **54/54** requests. Native decode output
gates passed **15/15** for each of code, prose and structured generation; no additional
quality audits were run. Finish reasons were **45 stop and 117 length**: the latter
are the 54 bounded prefill and 63 bounded concurrency responses. There were zero
code output-budget stops. Four-rank snapshots show exactly **54 API successes per
run**, no extra requests, unchanged containers/workers and health 200 afterward.

KV remains **15 GiB per rank and 1,344,328 tokens**. The same baseline host observers
and GPU allocator probes recorded no OOM, allocation retry or host OOM kill during
any of the 12 rank/run windows. Rank-0 minimum available RAM was **2.12 / 2.99 / 3.01
GiB**, versus **2.22 / 2.23 GiB** in the reference. The lowest observed margin was
therefore slightly smaller in E03's first run; later runs did not show progressive
memory loss. Rank-0 sampled allocated CUDA memory peaked at **99,314.6 MiB** across
the series, versus **99,729.6 MiB** in the two reference runs. These sampled allocator
values do not cover all unified-memory consumers.

## Recipe and activation

The [candidate](../../../scripts/node/experiments/e03/README.md) ports the SparkRing
mHC package at `61f277bd0c97fbff892668e12ea04a330a45fa01` onto R10 FP8, adapting
ownership to TP4/DCP1. Attention and FFN retain full inputs. Per-call TP reduction
deferral feeds reduce-scatter and local mHC; all-gather reconstructs the complete
consumer input, final output and every DFlash2 auxiliary capture in original order.

R10, FP8 mapping, E20 hybrid projections, DFlash2, scheduler, CUDA graph settings,
15 GiB KV per rank and the 262,144-token context limit are unchanged. Isolated mounts
and a separate SparkCache namespace preserve the base. Decode, mixed batches and
other row counts use the ordinary path.

The corrected candidate passed 11 CPU tests and 88 model-free GPU comparisons
(22 per rank) before loading. Constructed sums and row order were exact. BF16
collectives and B12X pre, deferred post/pre and post passed `atol=0.03125`,
`rtol=0.02`: maximum absolute error 0.125, maximum relative L2 error 0.00310415.
The maximum elementwise relative error, 23,437.5, occurs near zero and is covered
by the absolute tolerance; bitwise equality is not required for reordered BF16 sums.
[Full numerical evidence](../../historical_benchmarks/experiments/2026-09-19-e03/corrected-preload-checks.json)
retains each comparison and its source receipt hash.

One corrected-candidate load passed both documented functional gates in 3.21 seconds.
All four source/cache identities, E20 signatures and allocator probes matched.
A separate 8,192-token API request demonstrated the actual 6,912-row chunk on every
rank: **90 reduce-scatter, 95 all-gather, including five DFlash2 auxiliary gathers**.
The engine retained **1,344,328 KV tokens**. These three validation requests are
separate from Rigmark.

## Measurement protocol

Rigmark source, prompt hash, comparison ID, seed, request body, token limits and
concurrency settings match the frozen reference. Each native execution had 15 decode
requests, 18 prefill requests (three cold/replay pairs at 8K, 32K and 64K), and
21 concurrency requests (three rounds at C1/C2/C4). Each run retains one fresh salt
across its cold/replay pairs. The corrected weight load stays in place across the
series, with the same host-memory observer source and intervals as the baseline.

For all 16 metrics, comparison uses the median of three native per-run values
against the fixed two-run baseline median. Integrity, errors, finish reasons and
native output gates use explicit totals. Normal output-budget stops remain in the
measurements; generated-answer quality is not a performance acceptance gate.

## Initial admission correction

The initial 8,192-target-row guard could not activate: R10 reserves five DFlash2
slots inside the 8,192-token input budget, then aligns ordinary full prefill chunks
to 2,304-token checkpoints, yielding 6,912 rows. The owner authorized this admission
correction and one coordinated corrective transition. The initial attempt had zero
native benchmark runs; it is superseded, with its
[original result](../../historical_benchmarks/experiments/2026-09-19-e03/initial-results.json),
[source pins](../../historical_benchmarks/experiments/2026-09-19-e03/initial-source-manifest.json)
and [scheduler evidence](../../historical_benchmarks/experiments/2026-09-19-e03/scheduler-eligibility.json)
retained separately. The two attempts required two total loads; the benchmark series
uses only the corrected load.
